# Feed protocol

The optional publisher targets a GitHub repository containing a feed tree. It is independent of deployment infrastructure. The source of truth is the publisher's typed structures and the shared [public feed validator](../pkg/publicfeed).

## Artifacts and identity

The [segment manifest](../internal/publisher/segment.go) locates segmented brief data and records checksums and counts. The publisher also maintains CVE enrichment metadata and change records. Public Markdown lives under `site/content/briefs/`; STIX 2.1 is an additional projection, with application-specific `x_craftedsignal_*` fields retained for compatibility. These field names are a wire format and do not change when the binary is renamed.

A brief ID identifies the durable entity; a slug is its public path; an event ID groups incident identity; a revision describes a change. Timestamps and IDs are preserved where consumers depend on them. Segment placement and manifest indexes are implementation details consumers should read from the manifest instead of guessing from a date.

Regular publication stages related files in one Git commit/ref update so consumers can read a consistent revision. Pin a repository commit while reading several files. Checksums detect mismatches against that manifest; they do not independently prove who published it.

## Public wrapper

The legacy `feed_public_key` name is retained for protocol compatibility. A 32-byte hex value feeds deterministic symmetric key derivation with a public salt; AES-GCM wraps payloads with random nonces. A public reader holding that value can also construct GCM-valid payloads. It provides neither confidentiality against feed consumers nor publisher signatures. Repository and delivery-channel integrity remain essential.

Do not put confidential or access-controlled material in a publicly distributed wrapped segment. A future private feed would require a separately designed and reviewed access and cryptographic contract.

## Projections and correction

Public Markdown deliberately omits rule queries, IOC values, full body content, and priority fields. That filtering does not apply automatically to another artifact. STIX export validates the supported object graph and references; it is not a claim of complete support for every STIX construct or every consumer.

Use `drafts amend` for reviewed corrections and `drafts retire-duplicates` or `bundle retire-briefs` for identity consolidation. These operations coordinate canonical data and derived artifacts. Back up state and preview before applying. See [commands](commands.md) for mutation semantics.

The [synthetic STIX example](../examples/stix-bundle.json) is generated by the exporter and checked with its validator. It contains fictional content and is not an intelligence feed. Schema and behavioral changes need consumer compatibility tests and release notes before publication.
